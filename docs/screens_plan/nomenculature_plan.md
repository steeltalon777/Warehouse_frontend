## 0. Назначение документа

Документ описывает пофазный план перехода раздела номенклатуры с текущего Django SSR на Angular SPA.

План ограничен функциональностью номенклатуры:

- дерево категорий;
- динамическая работа с деревом категорий;
- полный CRUD категорий;
- полный CRUD ТМЦ;
- полный CRUD единиц измерения;
- поиск, фильтры, пагинация и быстрые действия;
- merge/split справочных сущностей, если они остаются частью рабочего места номенклатуры;
- интеграция Angular UI в Django runtime.

План не переносит весь web-клиент сразу. Сначала переносится один bounded context: номенклатура.

## 1. Текущее состояние

### 1.1. Backend и источник истины

SyncServer остаётся единственным источником истины для складских доменных данных, прав доступа, справочников, операций и остатков.

Django web-клиент не должен становиться альтернативным владельцем справочников. Все чтение и изменения номенклатуры должны проходить через SyncServer API либо через Django BFF слой, который сам использует существующие SyncServer client wrappers.

### 1.2. Текущий SSR раздел

Сейчас маршрут номенклатуры подключён в Django:

- `Warehouse_web/config/urls.py` подключает `apps.catalog.nomenclature_urls` на `/nomenclature/`;
- `Warehouse_web/apps/catalog/nomenclature_urls.py` содержит маршруты дерева, категорий, ТМЦ, единиц, merge и split;
- `CatalogHomeView` редиректит на текущий SSR экран дерева;
- `NomenclatureTreeView` рендерит текущий экран дерева;
- `CategoryCreateView`, `CategoryUpdateView`, `CategoryDeleteView` обслуживают SSR формы категорий;
- `ItemCreateView`, `ItemUpdateView`, `ItemDeactivateView`, `ItemMergeView`, `ItemSplitView` обслуживают SSR формы ТМЦ;
- `UnitCreateView`, `UnitUpdateView`, `UnitDeleteView` обслуживают SSR формы единиц.

### 1.3. Текущий frontend проект

`Warehouse_frontend` сейчас является минимальным TypeScript placeholder проектом. Его нужно превратить в Angular workspace и сделать основным домом нового SPA кода.

## 2. Архитектурное решение

Решение: Angular исходники живут в `Warehouse_frontend`, а Django на переходном этапе остаётся host и BFF для SPA.

Целевая схема переходного периода:

```text
Browser
  -> Django /nomenclature/
    -> Angular SPA shell
      -> Django BFF endpoints /nomenclature/api/*
        -> Warehouse_web sync_client services
          -> SyncServer /api/v1
```

Финальная схема в рамках этого плана:

```text
Browser
  -> Django /nomenclature/
    -> production Angular assets из Warehouse_frontend build
      -> Django BFF endpoints
        -> SyncServer
```

Важно: финальная фаза этого плана означает полную интеграцию собранного Angular в Django runtime для раздела номенклатуры. Это не означает перенос Angular исходников внутрь `Warehouse_web`.

## 3. Почему не переносить всё сразу напрямую в standalone SPA

На первом этапе Angular не должен напрямую ходить в SyncServer из браузера.

Причины:

- Django уже держит web session и login flow;
- Django уже знает текущего пользователя;
- Django уже содержит связку пользователя с SyncServer контекстом;
- Django уже централизует права доступа к catalog management;
- не нужно отдавать долгоживущие SyncServer tokens в браузер;
- проще сохранить CSRF, logout, redirects и audit;
- проще откатиться на SSR route при проблемах.

Standalone deployment можно рассматривать позже, когда будут стабилизированы web auth, CORS, token rotation, contract tests и release pipeline.

## 4. UX цель рабочего места номенклатуры

Новый Angular экран должен быть не набором отдельных страниц, а единым рабочим местом.

Базовая компоновка:

```text
┌──────────────────────────── Номенклатура ────────────────────────────┐
│ Поиск, быстрые фильтры, кнопки создания, статус синхронизации          │
├──────────────────────┬──────────────────────────────┬────────────────┤
│ Дерево категорий     │ Список ТМЦ                   │ Правая панель   │
│                      │                              │                │
│ - раскрытие веток    │ - таблица                    │ - карточка      │
│ - поиск по дереву    │ - поиск                      │ - форма         │
│ - выбранная ветка    │ - фильтр категории           │ - действия      │
│ - быстрые действия   │ - пагинация                  │ - ошибки        │
└──────────────────────┴──────────────────────────────┴────────────────┘
```

Основной сценарий пользователя:

1. открыть `/nomenclature/`;
2. увидеть дерево категорий;
3. выбрать категорию;
4. увидеть ТМЦ в выбранной категории;
5. создать дочернюю категорию или ТМЦ из текущего контекста;
6. отредактировать карточку без ухода со страницы;
7. увидеть обновление дерева или таблицы без полной перезагрузки страницы.

## 5. Общие правила миграции

- SSR не удаляется до подтверждения полного покрытия Angular функциональностью.
- Angular сначала запускается в read-only режиме.
- Мутации переносятся по одной группе: категории, ТМЦ, единицы, сложные действия.
- Все мутации проходят через Django BFF и SyncServer.
- Старые Django формы остаются fallback до финальной фазы.
- Каждый новый JSON endpoint покрывается тестами Django.
- Каждый основной Angular сценарий покрывается UI smoke тестами.
- Для длинных списков обязательны пагинация, debounce поиска и защита от лишних запросов.
